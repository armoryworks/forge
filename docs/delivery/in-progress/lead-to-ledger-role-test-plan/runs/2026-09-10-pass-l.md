## D-1 — CRITICAL: enabling CAP-ACCT-FULLGL deadlocks order-to-cash

**No role can send an invoice while the ledger is on.** `SendInvoice` posts AR inline, and the GL
segregation-of-duties authorizer grants `PostJournalEntry` to `Controller` only. But `Controller` is
not on `InvoicesController` (Admin/Manager/OfficeManager).

| Role | Result |
|---|---|
| Admin, Manager, OfficeManager | 403 `does not hold the GL capability PostJournalEntry` |
| Controller, PM, Engineer | 403 from the controller's own role gate |

Verified by granting `Controller` to the Admin user: the same call then returned 204 and posted.
So the install is only usable by a person holding **both** `Controller` and one of
Admin/Manager/OfficeManager — which `CurrentUserCapabilities` is explicitly designed to prevent as a
separation-of-duties violation. This plausibly explains why the GL "has never posted a real dollar"
at either design partner: with the shipped role set it structurally cannot.

Same shape applies to `CreatePayment`, `ApproveVendorBill`, `ReceiveItems` and every other inline
posting call site.

## D-2 — the Procurement role has zero effective grants, not one

`PurchaseOrdersController` is class-level `[Authorize(Roles="Admin,Manager,OfficeManager")]`, and
short-close adds `[Authorize(Roles="Admin,Manager,OfficeManager,Procurement")]`. ASP.NET Core
composes multiple `[Authorize]` attributes with **AND**, so a Procurement-only user fails the class
check and the action-level grant is dead code. Measured: 403. The plan's §9.3 said "exactly one
grant" — it is zero. A buyer can do nothing.

## D-3 — "disabling FULLGL is ungated" is false

Documented in `forge-api/CLAUDE.md`, in this plan's L-0.5, and in the shared memory note. The code
refuses with 409 `capability-gl-live-ledger` once opening balances exist, directing the operator to
the governed deactivation cutover. Behaviour is correct and covered by
`ToggleCapabilityFullGlGateTests`; the docs are stale. Note the practical consequence: **enabling
FULLGL on an install is effectively one-way through the API.**

## Plan corrections

1. The opening journal **cannot** be all-zero — the validator requires exactly one of debit/credit
   non-zero per line. Use a real balanced pair.
2. Capability listing is `GET /api/v1/capabilities/descriptor`; `/api/v1/capabilities` is 404.
3. `CreatePaymentCommand` field is `method`, not `paymentMethod`.
4. Under-applying a payment is **legal**, not a 400 — the remainder credits `CUSTOMER_DEPOSITS`.
   §L-11.1's "Σ Applications must reconcile to Amount" is wrong; §L-11.4 covers the real behaviour.
5. Setting a quote/order tax rate that differs from the customer's computed default requires a
   verified tax certificate (`TaxOverrideGuard`) — 409. Not in §2.3's preconditions.
6. Creating a shipping label additionally needs a **customer shipping address** and a **default
   company location**. Neither is in §2.3.
7. `UpdateShipmentCommand` exposes only a legacy free-text `Carrier`; the carrier FK cannot be
   changed after creation.
